# 08. リスクと対策

## 技術リスク

### R1. psd-tools での複雑な PSD 生成が不安定
- **影響**: 大。PSD 出力は本プロダクトの最終価値。
- **対策**:
  - PsdExporter を抽象化し、複数実装を用意(設計済み)。
  - 生成後に必ずラウンドトリップ検証(再読込 → レイヤー名/階層/ピクセル比較)。
  - 失敗時は LayerZip + Photoshop JSX スクリプトへ自動フォールバックし、ユーザーに明示。
  - Step 11 の最初に「グループ階層 + 大量レイヤー + 4096px」のスパイクテストを行い、限界を早期把握。

### R2. 簡易セグメンテーション(ManualBox)の品質が低く、MVP の体験が悪い
- **影響**: 中。MVP は「マスクを人が直せる」ことが前提。
- **対策**:
  - マスク編集 UI(ブラシ + refine)を MVP 必須機能として先に完成させる(human-in-the-loop の核)。
  - アルファ付き入稿画像では背景アルファを最大活用(切り抜き精度が大きく向上)。
  - quality_report に「簡易マスク由来」を明記し、期待値を制御。
  - SAM2Segmenter のインターフェース・タスクスキーマ(box/point/negative)を最初から用意し、Phase 2 で差し替えのみで品質向上できるようにする。

### R3. 大画像(4096px+)でのメモリ・速度問題
- **影響**: 中。商用立ち絵は 4K〜8K が普通。
- **対策**:
  - 内部処理は working サイズ(長辺 2048 等)で行い、最終出力時のみフル解像度で再実行する 2 段階方式を設計に組み込む(マスクはフル解像度へアップスケール + refine)。
  - レイヤー生成をパーツ単位で逐次処理し、全レイヤーの同時メモリ保持を避ける。
  - プレビューは縮小版で高速化。

### R4. フロントのキャンバス座標系バグ(ズーム/パンで bbox・ブラシ座標がずれる)
- **影響**: 中。位置ずれは Live2D 品質要求に直結。
- **対策**:
  - 「保存座標は常に正規化画像ピクセル座標、ズームはビュー変換のみ」を規約化。
  - 座標変換ユーティリティを 1 箇所に集約し Vitest で単体テスト。

### R5. Tauri のサイドカー(Python)配布が複雑
- **影響**: 小〜中(MVP はブラウザ + ローカルプロセスで回避可能)。
- **対策**:
  - MVP はブラウザ動作を正とし、シェルは起動スクリプトレベルに留める。
  - 配布時は PyInstaller で API を単一バイナリ化 → Tauri sidecar 登録。問題があれば Electron へ切替(シェル依存を最小化する設計済み)。

## プロダクトリスク

### R6. Live2D Cubism の PSD インポート仕様への不適合
- **影響**: 大。読み込めなければ価値ゼロ。
- **対策**:
  - Live2D 制約(RGB/8bit/レイヤーマスク不使用/クリッピング不使用/名前重複禁止)を quality_check と export 前バリデーションの両方で強制。
  - 実機検証を Step 11 の DoD に含め、Cubism Editor(無料版)での読込テストを繰り返す。

### R7. パーツ分けの粒度がユーザー期待と合わない(細かすぎ/粗すぎ)
- **影響**: 中。
- **対策**:
  - ヒアリング(品質レベル・可動要件)でテンプレート粒度を調整(MockAnalyzer 段階から実装)。
  - パーツ追加/削除/統合を PartsEditor で自由に行えるようにし、テンプレートは出発点と位置付ける。

### R8. 「AIで全自動」への期待過剰
- **影響**: 中(評判リスク)。
- **対策**: UI 文言・README で「AI 9割 + 人の仕上げ 1割」を一貫して明示。品質スコアで客観的な完成度を提示。

## 開発プロセスリスク

### R9. 雑な実装が将来の高精度化を妨げる
- **影響**: 大(明示的な品質要求)。
- **対策**:
  - Analyzer / Segmenter / Exporter / Inpainter の 4 抽象化は Step 6-11 の各実装前にインターフェースを先にコミット。
  - パス管理を core/paths.py に一元化し、レビューで直書きパスを拒否。
  - 画像処理は純関数 + pytest 必須(スナップショットテスト)。

### R10. スキーマの Python/TS 二重管理による乖離
- **影響**: 中。
- **対策**: Pydantic を唯一の定義元とし、TS 型は JSON Schema から自動生成(手書き禁止)。CI で生成物の差分チェック。

## セキュリティ/堅牢性

- files 配信 API のパストラバーサル対策(プロジェクトルート外への解決を拒否)。
- アップロードファイルの MIME/マジックバイト検証、サイズ上限(config で 64MB 等)。
- 外部 AI API キーは環境変数 + 任意(なくても全機能がモックで動作)。キーをプロジェクト JSON に保存しない。
